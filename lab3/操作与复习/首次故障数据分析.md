# 悬停翻转：第一次真实数据排查

## 小白先看结论

通信正常，目标也是(0,0,2)米；首要问题是之前给的姿态增益过大，控制命令反复猛烈纠正，造成振荡。先把kr从30降为3、komega从10降为1，kx=6、kv=4保留。这个调整依据真实数据和简化模型，仍需TESSE重新运行确认。

## 现在怎么重试

1. 在运行控制器的终端按Ctrl+C。
2. 点击Unity，按R重置；保持仿真器、桥接、RViz运行。不要在控制器仍运行时重置。
3. 控制器终端执行：

```bash
source /opt/ros/noetic/setup.bash
source ~/vnav_ws/devel/setup.bash
roslaunch controller_pkg traj_tracking.launch kx:=6 kv:=4 kr:=3 komega:=1
```

这是启动参数覆盖，不用重新下载、修改C++或编译。启动输出应显示kx=6、kv=4、kr=3、komega=1。继续使用STATIC_POSE=1的悬停模式。

观察约5秒。若仍剧烈翻转，立即在控制器终端按Ctrl+C，不连续放任运行。若稳定，再继续观察20秒，暂不切换圆轨迹。

## 再录一次数据

在启动控制器前，新开录包终端，执行：

```bash
source /opt/ros/noetic/setup.bash
source ~/vnav_ws/devel/setup.bash
rosbag record -O ~/lab3_evidence/hover_debug_gain3_1.bag /current_state /desired_state /rotor_speed_cmds /clock
```

控制器跑5—10秒后，先停控制器，再在录包终端按Ctrl+C保存。把hover_debug_gain3_1.bag和飞行现象发来，便于比较。

## 原数据里实际看到了什么

数据来源：用户上传hover_debug.bag。记录了约39.6秒状态，其中控制指令持续约27.1秒。

| 实测内容 | 结果 |
|---|---|
| 目标 | 固定位置(0,0,2)米，yaw=45度 |
| 控制开始的位置 | 约(0.003,-0.241,0.700)米 |
| 控制开始的yaw | 约-46.8度，与目标相差约91.8度 |
| 首条旋翼转速 | 约[866.5,-863.8,868.8,-861.4] rad/s |
| 全程最大旋翼转速绝对值 | 约3085.3 rad/s |
| 启动后表现 | 旋翼转速频繁正负切换，角速度剧烈来回摆动 |

负转速本身是本实验允许的，不应一律截成0。问题在于这次命令幅度和频繁反向过强。按题目质量和升力系数，理想水平静态悬停的四个转速约为49.5 rad/s；有偏航纠正时可以偏离该值，因此49.5只是量级参考，不是固定限幅。

## 为什么这次降低这两个参数

按课程分配矩阵计算，首条偏航力矩约29.94 N·m；启动后约0.02秒，机体系yaw角速度增加约5.98 rad/s。按J≈力矩×时间/角速度变化估计，启动瞬间的等效惯量约0.10 kg·m²。

这只是从首段数据得到的近似响应估计，不是精确标定；存在采样、延迟与物理引擎影响。它说明前次按单位惯量做的理想检查没有覆盖当前实际响应，因此之前kr=30、komega=10偏激进。此次两者降低10倍，先保留平移参数。

## 验证边界

已完成：读取真实bag、核对目标与状态、分析旋翼命令、检查分配矩阵；在包含采样与延迟的简化刚体模型中，新参数较旧参数明显稳定。

尚未完成：新参数在用户电脑TESSE中的实际悬停与圆轨迹验证。简化模型结果不作为真实飞行误差写入最终报告。

代码默认增益与指南已同步改为kr=3、komega=1。已安装的Ubuntu不会自动同步GitHub，直接使用上面的启动参数即可应用新值。不要为调这两个参数重复运行安装脚本，以免覆盖自己后续的轨迹修改。

报告可据实写：首次悬停出现姿态振荡；通过ROSbag发现旋翼指令剧烈反向，据此降低姿态和角速度反馈增益；调整后的效果待真实复测后补充。
